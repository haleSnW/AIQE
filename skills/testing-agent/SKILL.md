# 测试 agent 工作纪律（通用）

## 本 skill 为什么存在

测试类任务最容易出现两类「全绿但没意义」的事故：

1. **自证空转测试**：测试体内重新实现了一遍被测逻辑，或只断言自己
   现造的本地变量——产品代码坏了，测试照样绿；
2. **假完成汇报**：声称「已通过」但没运行任务书里的验收命令，或跑了
   但没核对预期输出。

本 skill 把「写/改测试」「跑验收」「汇报结果」三个动作的检查项固化
下来，供所有测试执行/审查角色共用。本 skill 是通用版；若项目有更具体
的项目级 skill，以项目级为准，本 skill 作为最低底线。

## 一、写/改一个测试之前，逐条检查

1. **这个测试 import 了被测的真实模块/函数吗？**
   测试体内重新实现了一遍要测的逻辑 → 这是自证测试，不是回归测试。
   停下来，改成调用真实实现。

2. **这个测试断言的是「产品行为」还是「数据自身性质」？**
   `assert len(x) > 1000` 而 `x` 是测试函数自己现造的、没经过产品代码
   处理的变量 → 断言测的是语言本身。重写。

3. **如果产品代码被故意改错，这个测试会失败吗？**
   写完做一次思想实验（或真改一行验证）：给被测函数塞一个明显 bug
   （返回值取反、删一个处理分支），测试仍绿 = 没有保护力，重写。

4. **硬编码的常量/魔数是从哪抄来的？**
   测试里的标签、正则、阈值应引用产品代码的同一来源（同一模块级常量），
   而不是各自手打一遍——两份独立维护的「应该一致」迟早漂移。

5. **这个测试需要真实硬件/网络吗？**
   需要就用依赖注入/monkeypatch 让核心逻辑可离线测，而不是整组跳过、
   又没人发现它从来没真正跑过。

## 二、修复 bug 后加回归测试：必须红→绿

只做「修复后测试变绿」这一步等于没做——测试可能从写出来那一刻起就是
空转的。必须两步都做：

1. 先写测试，在「bug 还在」的版本上运行，**确认它真的失败（红）**；
2. 再应用修复，确认它变绿；
3. 把「红→绿」验证过程写进 commit message 或任务书回贴，方便审查者
   核实——不要只贴一行「全部通过」。

## 三、验收命令纪律（执行者）

- 任务书里的每一条验收命令都要**实际运行**，并把输出原样回贴（含
  预期输出对照）。不运行、不核对 = 任务未完成。
- 验收命令的预期输出是文本级别的（如 `91 passed`），不是形容词
  （「应该没问题」）。贴输出时注明是否与预期一致。
- 涉及真机/网络的验收命令：环境不具备时如实报告 NOT_ASSESSED，
  绝不假装跑过。

## 四、边界声明（执行者与审查者）

- 只改任务书边界内的文件；边界外的发现问题，记录并上报，不顺手改。
- 不引入新依赖；不重构任务书范围外的代码；不改协议（除非任务书明确）。
- 审查者每条结论必须带证据（文件:行号 + 复现输出），不凭印象。

## 五、汇报格式（完成任务时）

```
任务书编号: T-<编号>
完成内容: <改了什么，指向具体文件>
验收命令输出:
  <命令1> → <输出，标注 与预期一致/不一致>
红→绿验证: <有/无；有则附两轮输出>
边界外发现: <无，或列出待上报项>
```
