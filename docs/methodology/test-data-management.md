# 测试数据管理（Test Data Management）

> 用例集、基线、报告是评估体系的**三类资产**，各自的存放、版本化、
> 更新与隐私策略不同。混放是数据管理事故的头号来源。

---

## 1. 三类数据与目录约定

| 数据类型 | 内容 | 建议存放 | 是否进 git | 更新频率 |
|---|---|---|---|---|
| **用例集** | TestCase 定义（代码） | 项目内 `src/<pkg>/cases/`（本仓库 `src/AIQE/cases/`） | ✅ 随代码提交 | 随需求/验收标准变化（低频） |
| **基线** | 历史分数参考（JSON） | 仓库内 `baselines/`（或 `tests/baselines/`） | ✅ 建议进 git（见第 2 节） | 随「基线更新 SOP」（见第 3 节） |
| **报告** | 每次跑分结果（JSON + 摘要） | 仓库外（CI artifact / `~/.AIQE/results` / 共享存储） | ❌ 默认不进 git | 每次跑分产生（高频） |

**本仓库的落地现状**（作为参考）：

```
src/AIQE/cases/        # 用例集（代码资产，随版本演进）
~/.AIQE/results/       # 默认基线目录（RegressionAnalyzer 默认路径）
examples/.regression-demo/  # 示例专用数据（gitignore，演示不污染正式基线）
AIQE-report-*.json     # 报告产物（gitignore）
```

**一条红线**：报告是「每一次的结果快照」，基线是「人工选定的参考版本」——
两者混在一个文件里、或脚本把当前分数自动当基线，回归检测就失效了
（详见 INTEGRATION.md 基线管理 SOP 的「禁止更新」场景）。

## 2. 基线 JSON 纳入 git 版本管理

基线进 git 的三个理由：可回溯（哪个版本定的基线）、可 diff（基线变化
可审查）、可复现（checkout 历史版本即可重放当时评估）。

推荐目录与命名：

```
baselines/
    baseline.json              # 当前生效基线（RegressionAnalyzer 解析的顶层 dict 或报告嵌套格式）
    baseline-2026-08-15.json   # 历史快照（按日期归档，随决策保留）
```

**基线文件内容规范**：
- 顶层 dict 格式：`{"<case_id>": <score>, ...}`；
- 或 EvaluationReport 嵌套格式（`{"test_plan_id":..., "cases":[...]}`，
  直接复用报告文件做基线，保留 prompt 与判分明细）；
- 建议在同一提交里**附带一份说明**（改了什么、为什么），如
  `baselines/CHANGELOG.md` 或 commit message——基线改动与代码改动一样
  需要审查轨迹。

**git 操作纪律**：
- 基线更新与代码改动同 PR/同 commit，便于审查「改代码同时改基线」的
  因果；
- 禁止把「分数下降时的当前报告」直接覆盖基线提交（作弊模式）；
- 报告产物不进 git（高频噪音），要进 git 的只有基线。

## 3. 基线更新 SOP

触发条件与动作（与 INTEGRATION.md 第 4 节呼应）：

| 触发场景 | 动作 | 是否允许 |
|---|---|---|
| 用例集变更（增删改用例） | 重跑全量 → 新分作为新基线 | ✅ 必须 |
| 评分器规则变更 | 先重跑全部历史用例验证新旧分趋势一致 → 再更新基线 | ✅ 有条件 |
| 模型升级且连续跑分稳定 | 新分定为新基线 | ✅ 建议 |
| 基线过期（周期刷新，如 30 天） | 当前配置重跑一次刷新 | ✅ 建议 |
| 分数下降 | 更新基线 | ❌ 禁止——先排查回归原因 |

**更新流程**（五步）：

1. 在 `baselines/` 下新建候选文件 `baseline-<日期>.json`（当前配置跑分结果）；
2. 与旧基线 diff，逐条解释差异（哪个用例升了/降了、为什么）；
3. 跑一次「候选基线 + 当前报告」的回归对比，确认结论合理；
4. 用候选文件替换 `baseline.json`，连同说明一起提交；
5. 归档旧版本为历史快照（或依赖 git 历史，删除冗余副本）。

## 4. 隐私注意：用例数据脱敏

用例集是**代码资产**，会随仓库分发（开源/内部分发）——用例里嵌入真实
数据 = 数据泄漏：

| 风险场景 | 示例 | 处置 |
|---|---|---|
| 用例 prompt 含真实用户消息 | 「用户张*抱怨订单…」 | 替换为虚构等价样本（保留格式特征，去掉可识别信息） |
| 预期输出含真实回复/日志片段 | expected_keywords 抄自线上日志 | 只保留关键词特征，不整段复制真实输出 |
| 基线/报告含真实输入输出 | 报告 JSON 的 prompt/response 字段 | 报告不进 git；进共享存储时做脱敏再归档 |
| 账号/密钥/内网地址 | prompt 里出现 token、域名、IP | 一律替换为占位符（`<TOKEN>` / `example.com` / `10.0.0.0/8` 示例网段） |

**自检命令**（提交用例集/基线前）：

```bash
# 扫描常见敏感模式（token/私钥/邮箱/内网 IP），按需收紧
grep -rniE "(sk-[a-z0-9]{16,}|api[_-]?key|password\s*[:=]|[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}|10\.\d+\.\d+\.\d+|192\.168\.)" src/ baselines/ 2>/dev/null || echo "未发现常见敏感模式"
```

**原则一句话**：用例集与基线里只该出现「虚构的等价样本」，真实数据
只允许出现在不进 git 的本地报告里，且归档前按需脱敏。
