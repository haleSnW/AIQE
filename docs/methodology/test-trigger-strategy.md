# 测试触发策略（Test Trigger Strategy）

> 分层框架（testing-layers.md）回答了「测什么」，本档回答「**什么时候
> 跑**」：四档测试 × 自动/手动触发矩阵。目标是——每次改动都有合适的
> 档位被触发，既不过测（浪费）也不漏测（风险）。

---

## 1. 四档定义与范围

把 12 层测试分配到四个档位，按**速度从快到慢、触发频率从高到低**排序：

| 档位 | 包含层级 | 量级 | 何时触发 | 成本 |
|---|---|---|---|---|
| **① 冒烟（Smoke）** | 单元 + 接口（契约） | 秒级 | **每次改动**（任何代码/用例变更后） | 秒 |
| **② 全量（Full）** | 集成 + 功能 + 黑盒 | 分钟级 | **每日 / 合并前** | 分钟 |
| **③ 回归（Regression）** | 性能 + 基线对比 | 分钟级（真机可长） | **换模型 / 改评分器 / 基线更新时** | 分钟~小时 |
| **④ 验收（Acceptance）** | 端到端 + 稳定性 + 安全 + UI + 灰盒 | 分钟~小时级 | **发布前 / 需求完成时** | 分钟~小时 |

**档位与层级的关系**（12 层 → 4 档）：

```
① 冒烟    单元 / 接口（契约）
② 全量    集成 / 功能 / 黑盒
③ 回归    性能 / 基线对比（回归判定）
④ 验收    端到端 / 稳定性 / 安全 / UI / 灰盒
```

**设计意图**：档位是「触发器」的单位，层级是「测什么」的单位——一次
「改评分器」的提交触发③档，内部实际跑的是「性能对比 + 全量用例集重跑」
（改评分器必须重跑历史用例，见 testing-layers.md 决策表）。各档内部
具体跑哪些层级，由项目按 testing-layers.md 的决策表裁剪。

## 2. 自动触发（harness hook / CI）

### 2.1 开发 harness hook 时机

以 Claude Code 类 harness 的 hook 时机为例（时机名通用，其他 harness
按等价时机映射）：

| Hook 时机 | 挂哪一档 | 触发条件 | 预期耗时 |
|---|---|---|---|
| `SessionStart` | 不跑测试，仅检查基线存在性 | 每次会话开始 | 秒 |
| `PreToolUse`（写测试/改用例文件前） | 不跑测试，输出「本次改动应触发哪档」提示 | 工具涉及 src/tests/cases 目录 | 秒 |
| `Stop`（一次改动完成后） | **① 冒烟** | 任何代码/用例变更 | 秒级，可安心挂在每次停止 |
| `SessionEnd` | **② 全量**（当日累计改动 ≥ 1 次时） | 会话结束时累计变更存在 | 分钟级，提示后执行 |

要点：**Stop 挂冒烟、SessionEnd 挂全量**——冒烟足够快不打断工作流，
全量放到会话边界避免反复跑。

### 2.2 CI 时机

| CI 事件 | 挂哪一档 | 说明 |
|---|---|---|
| push / PR（每次提交） | ① 冒烟 | 秒级，快速失败；mock 后端确定性结果可安心阻断 |
| PR 合并前（required check） | ② 全量 | 分钟级；报告作为 PR 检查项 |
| 定时（每日/每周） | ② 全量 + ③ 回归（基线趋势） | 基线漂移预警，报告归档 |
| 发布流水线 | ④ 验收 | gated 真机用例在此档开启；门禁五状态判定 |

### 2.3 「改了 X → 自动跑 Y 档」决策表

| 变更 | 自动触发档位 | 理由 |
|---|---|---|
| 改用例（增删/改 prompt/改关键词） | ① 冒烟 + ② 全量 | 用例是规格，改它要验证用例本身合法且分数有区分度 |
| 改评分器（judge 规则） | ③ 回归 + ② 全量 | 度量本身变了：先跑历史用例证明新旧分可比，再全量重跑 |
| 换模型（版本/量化/后端） | ③ 回归 | 全量用例集对比基线，五步流程（见 INTEGRATION.md 第 5 节） |
| 改执行器/后端协议 | ① 冒烟（契约测试） | 协议破坏最先在契约层暴露 |
| 改报告/输出格式 | ① 冒烟 + ② 全量（报告断言） | 输出是下游消费方的契约 |
| 发版（tag/release） | ④ 验收 | 全部门禁 + 人工判定 |
| 仅改文档 | 不触发 | 无代码变更 |

## 3. 手动触发（什么时候必须手动）

以下场景**不能**靠自动触发，必须由人显式发起：

| 场景 | 为什么必须手动 | 手动动作 |
|---|---|---|
| 需要真机/真实模型 | 自动触发环境（CI/沙盒）无模型或资源受限 | `/aiqe-acceptance`（含真机用例） |
| 需要人工判断 | WARN 的处理、MANUAL_REVIEW 裁决、灰度观察 | 人看报告 + 回填结论（五状态词汇见 process-management.md） |
| 长时间 soak / 稳定性 | 小时级，不适合挂在每次改动 | `/aiqe-acceptance` 的 soak 子命令 |
| 基线更新决策 | 涉及「该不该更新基线」的判断（SOP 见 test-data-management.md） | 人按五步流程执行 |

配套的 `skills/aiqe-testing/SKILL.md` 提供手动命令映射（/aiqe-smoke、
/aiqe-full、/aiqe-regression、/aiqe-acceptance）——把「手动」也做成
**固定动作**，而不是临时拼命令。

## 4. 四原则

1. **能自动不手动**：凡能写成确定性命令的触发，一律进 hook/CI；手动
   只留给「需要真机/需要判断」的场景。
2. **快档先行**：冒烟不过不进全量，全量不过不进回归——档位是门禁
   链，不是可选项清单。
3. **回归永远先于验收**：验收前必须有一次完整的回归对比（验收回答
   「能不能发」，回归回答「相对上次差没差」——没有后者，前者是空中楼阁）。
4. **手动档必须留痕**：谁、何时、什么结果——手动跑完把输出归档进
   报告/任务书回贴，禁止「我手动跑过了」一句话了事。
