# AIQE 质量流程管理（Process Management）

> AI 质量评估不是一条命令，是一条**流程**：从需求到决策，每个环节都有
> 明确的进出标准。本文档定义全生命周期、质量门禁五状态词汇与发布判定
> 规则，全部通用化——不依赖任何具体产品形态。

---

## 1. 全生命周期：七环节

```
需求 → 用例设计 → 执行 → 评分 → 回归 → 报告 → 决策
 │        │         │      │      │      │      │
 │        │         │      │      │      │      └─ 发布 / 回退 / 迭代 / 观察
 │        │         │      │      │      └─ 结论供人读、JSON 供机器读
 │        │         │      │      └─ 与基线对比，产出 new/pass/degraded/regression
 │        │         │      └─ 确定性评分（关键词/长度/格式）
 │        │         └─ 后端执行（mock 离线 / 真机在线）
 │        └─ 用例即规格：把期望编码成 TestCase
 └─ 起点：可测的验收标准（见 requirement-analysis.md）
```

每个环节的进出标准：

| 环节 | 输入（进） | 输出（出） | 完成标准 |
|---|---|---|---|
| 需求 | 模糊需求/变更请求 | 可测验收标准 | 每条标准能用「响应是否包含 X / 长度是否 ≥ N / 格式是否合法」描述（见 requirement-analysis.md） |
| 用例设计 | 验收标准 | TestCase 集合 | 每条验收标准 ≥ 1 个用例；用例字段完整合法（见 templates/test-case-template.md）；用例能独立跑通产生有意义分数 |
| 执行 | 用例集 + 后端 | ExecutionResult 列表 | 全部用例执行完毕，失败有 error 记录而非静默跳过；真实后端 gated |
| 评分 | ExecutionResult | JudgeResult（score/checks/reasons） | 评分确定性：同响应同分数；评分规则与用例类别匹配（json/coding 走格式分支） |
| 回归 | JudgeResult + 基线 | RegressionResult（new/pass/degraded/regression） | 基线存在性已核对；无基线时标 new 而非误伤 |
| 报告 | 全部结果 | JSON 报告 + 控制台摘要 +（可选）Markdown | 报告含执行/评分/回归三段字段；可追溯（trace_id/payload_hash） |
| 决策 | 报告 | 发布/回退/迭代/观察 + 基线更新 | 按第 3 节门禁规则判定；决策理由随报告归档 |

**失败回流**：任何环节输出不合格，流程回退到该环节的上一环，不带着
不合格产物继续往下走——例如评分规则改了就回流到用例设计（重跑全量），
不能直接出报告。

## 2. 质量门禁五状态词汇

所有评估结论统一收敛到五个状态，禁止自造词汇（避免「还行」「基本可以」
这类无法跨人跨期比较的描述）：

| 状态 | 含义 | 触发条件（示例） | 处置 |
|---|---|---|---|
| **PASS** | 全部通过 | 全部用例 passed 且无 regression | 可发布/可合并；按 SOP 更新基线 |
| **WARN** | 轻微下降，可观察期 | ≤ 2 个用例 degraded（下降 ≤ 阈值）或单项性能下滑 | 可发布但需人工抽检受影响用例的响应原文；下轮跑分重点关注 |
| **FAIL** | 阻断性退化 | ≥ 1 个用例 regression（下降超阈值）或关键用例 FAIL | 禁止发布；回退或修复后重跑 |
| **MANUAL_REVIEW** | 需人工判断 | 用例涉及主观质量（翻译地道性/风格一致性）；或状态为 new 的用例进入生产前 | 人工抽检 + 结论回填报告（reviewer 签名） |
| **NOT_ASSESSED** | 未评估 | 用例被跳过（真机 gated 未跑）/ 执行 error / 无基线且未观察 | 不计入通过率；在报告中明确列出未评估原因 |

**设计要点**：
- 五状态**正交**：WARN/FAIL 描述「与基线的差距」，MANUAL_REVIEW 描述
  「证据是否充分」，NOT_ASSESSED 描述「是否真的测过」——一个用例可以
  同时是 PASS + MANUAL_REVIEW（分数过了但质量主观，仍需人看）。
- NOT_ASSESSED 是最危险的漏网状态：跳过 ≠ 通过。报告中必须单独列出，
  且 gated 用例的默认状态就是 NOT_ASSESSED（防止「没跑过却显示通过」）。

## 3. 发布判定规则

发布判定 = 门禁状态 + 未评估情况，两条规则缺一不可：

```
规则 1（门禁）：存在 FAIL 状态 → 禁止发布，回到修复循环
规则 2（证据）：存在 NOT_ASSESSED 且其用例属于本次变更影响范围
                → 必须补跑后再发布（可发布=「已跑过的都过」≠「没跑过的也过」）
```

| 场景 | 判定 | 说明 |
|---|---|---|
| 全部 PASS，无 NOT_ASSESSED | ✅ 发布 | 标准放行 |
| 全部 PASS 但有 NOT_ASSESSED（gated 未跑） | ⚠️ 视影响范围 | 影响范围内 → 补跑；范围外 → 记录后放行 |
| 有 WARN（≤ 2 个轻微下降） | ⚠️ 观察期发布 | 人工抽检 + 记录跟踪项，下轮复查 |
| 有 MANUAL_REVIEW 且未回填结论 | ⏸ 等待 | 人工结论回填前不推进 |
| 有 FAIL | ⛔ 禁止 | 回退或修复，从「执行」环节重新进 |
| 全量 new（首次接入无基线） | 🔍 观察期 | 不发布为正式版本；跑通 N 次稳定后再定基线 |

## 4. 与开发 harness / CI 的衔接点

AIQE 流程不是独立运行的，它挂在开发 harness 的三个触发点上：

```
开发 harness（构建 / 提交 / 发布）
        │
        ├─① 每次提交（轻量）：mock 跑分 + 相关用例
        │     → 状态进 PR 检查，FAIL 阻断合并
        │
        ├─② 每晚/每周（全量）：全量用例集 + 基线回归
        │     → 报告归档，趋势进质量看板
        │
        └─③ 发布前（门禁）：五状态判定 + MANUAL_REVIEW 回填
              → PASS/WARN 放行，FAIL 阻断，NOT_ASSESSED 补跑
```

| 衔接点 | 跑什么 | 门禁效果 | 产物 |
|---|---|---|---|
| ① 提交级 | 相关用例（决策表见 testing-layers.md 第 3 节）+ mock | FAIL 阻断合并 | 报告 JSON + PR 评论 |
| ② 周期级 | 全量用例集 + 真实后端（可选） | 趋势预警（WARN 累计） | 归档报告 + 趋势数据 |
| ③ 发布级 | 全量 + gated 真机 + MANUAL_REVIEW | 五状态判定 | 发布检查单 + 归档报告 |

**门禁不是越严越好**：①级用确定性 mock（结果稳定，可放心阻断）；
③级真机结果波动大，默认「报告 + 人工判定」，确需硬门禁时只对
确定性后端启用。
