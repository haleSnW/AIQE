# AIQE 通用测试层级框架（Testing Layers）

> 一套任何 AI 项目都能直接套用的测试分层方法：12 个测试层级，每个层级
> 回答「测什么、在哪测、用什么测、哪些设施不自己建」。

**来源说明**：本文档将业界常见的测试分类整理为 12 类可迁移的分层方法，
表述已通用化——不绑定任何特定项目的模块名与硬件约束。文中「AIQE」指本
仓库，作为每一层「如何落地」的参考载体。

---

## 1. 十二层总览

| # | 层级 | 一句话定义 | 适用产品形态 | 在 AIQE 中如何落地 | 对应代码/测试文件 | 不建自研设施的边界 |
|---|---|---|---|---|---|---|
| 1 | **单元测试** | 对最小代码单元（函数/方法/类）独立验证其行为 | 全部形态（代码质量与产品形态无关） | 对执行器、评分器、回归分析器、报告器逐个模块断言行为 | `tests/test_runner.py`、`tests/test_schema.py`、`tests/test_backends.py` | 不引入 coverage/pytest-cov 门禁；需要度量时手动 `coverage run` 看数，不计入 CI 阻断 |
| 2 | **接口测试（契约测试）** | 验证组件之间的公开契约（方法签名/字段/状态语义）不被破坏 | 系统/OS 与 agent（协议/接口最多的形态）；模型后端接入 | `Backend Protocol` 用 `@runtime_checkable` 做结构性子类型检查，任何后端实现满足协议即被接受 | `src/AIQE/protocol.py`、`tests/test_backends.py`（isinstance 契约断言） | 契约断言只覆盖公开 API；不写 `inspect.getsource` 类源码守卫（重构即碎） |
| 3 | **集成测试** | 验证多个组件拼装后的协作行为 | 系统/OS、agent、APK/Web（多组件拼装形态） | 执行→评分→回归→报告整条流水线串联断言，`trace_id`/`payload_hash` 保证各阶段数据同源 | `tests/test_runner.py` 的流水线用例、`examples/quick_score.py`（冒烟） | 不建自研集成框架；pytest 的 `tmp_path`/`monkeypatch` 已足够 |
| 4 | **系统测试（端到端）** | 在真实或近似真实环境下验证完整流程 | 全部形态（发布前必跑） | 三个可运行示例脚本覆盖「mock 离线 → 真实 ollama → 回归对比」三种完整跑分流程；真实后端由环境变量 gated | `examples/quick_score.py`、`examples/ollama_backend.py`、`examples/regression_compare.py` | 真机/网络测试一律 gated（`MLX_EVAL_LIVE=1` 或等价开关），默认 `pytest` 不含 live 用例 |
| 5 | **黑盒测试** | 不关心内部实现，只从外部接口与用户视角验证行为 | APK/Web、系统/OS（对外部接口/用户可见行为敏感的形态） | 跑分脚本的 stdout 摘要、JSON 报告结构、退出码作为对外可验收契约 | `tests/test_runner.py` 的报告结构断言、`examples/*` 输出即验收 | 不做「启动真实进程喂 stdin」的重型黑盒；以示例脚本 + 文档化验收命令为主 |
| 6 | **白盒测试** | 基于内部实现结构设计用例，覆盖每个分支 | 算法、模型（逻辑分支密度高的形态） | 评分器全分支（空响应/关键词全半零命中/长度惩罚/格式分支/分数上限）、回归全状态（new/pass/degraded/regression）、执行器异常路径 | `tests/test_runner.py` 的分支矩阵 | 分支级细节只通过公开方法触发；私有函数由公开行为间接覆盖 |
| 7 | **灰盒测试** | 结合内部结构知识与外部接口做验证 | 系统/OS、agent（需要内部状态佐证行为的形态） | 协议满足性断言（结构检查）+ 关键内部状态断言（trace_id 贯穿、payload_hash 完整性） | `tests/test_runner.py` 的 trace_id/payload_hash 断言 | 内部状态只断言「对外可观察」的部分；不绑定私有实现细节 |
| 8 | **功能测试** | 验证产品功能按规格工作 | 全部形态（用例集即规格，形态无关） | 用例集即规格：标准用例 + 扩展用例 + 边界用例是对产品期望的编码，一次跑分即功能验收 | `src/AIQE/cases/`（4 标准 + 6 扩展 + 8 边界）、`tests/test_extended_cases.py`、`tests/test_boundary_cases.py` | 不新造测试框架；pytest 唯一，新增用例必须走真实产品代码路径 |
| 9 | **性能测试** | 验证吞吐、延迟、资源占用是否达标 | 模型、系统/OS（吞吐/延迟敏感形态） | 执行结果采集 `elapsed_sec`/`tok_per_sec`/`tokens_generated`，报告与基线留存性能字段 | `src/AIQE/runner.py` 的计时字段、`examples/*` 输出、`docs/INTEGRATION.md` 基线 SOP | 性能**不做自动门禁**（本地推理 tok/s 波动大），回归进报告人工判断；不建自研压测平台 |
| 10 | **稳定性测试** | 长时间/反复运行下资源有界、行为不劣化 | 系统/OS、agent、APK（常驻/长跑形态） | mock 后端确定性保证重复跑分可复现；`setup`/`teardown` 生命周期幂等且安全；soak 与内存有界性作为 gated 脚本 | `src/AIQE/backends/base.py` 的生命周期约束、`docs/INTEGRATION.md` 的 soak 建议 | soak/内存检测是 gated 脚本（真机时复用 psutil 等既有设施），非常驻测试 |
| 11 | **安全测试** | 验证系统对恶意/对抗输入的抵抗 | agent、APK/Web、系统/OS（对抗面大的形态） | 对抗性提示用例（断言「拒绝/不被诱导」关键词）、边界输入用例（全角/emoji/超长单行/空信息追问） | `src/AIQE/cases/boundary_cases.py`、`tests/test_boundary_cases.py` | 不建自研安全扫描器；bandit 等仅作可选 dev 依赖手工使用；注入类用例复用既有评分机制，零新依赖 |
| 12 | **UI 测试** | 验证用户可见输出的呈现与文案 | APK/Web、系统/OS（有用户界面的形态） | 控制台条形图摘要的精确文本断言（capsys），无截图、无浏览器 | `tests/test_runner.py` 的 `print_summary` 渲染断言、`examples/*` 的终端输出 | 不上 playwright/selenium/快照库；文本断言已足够且零依赖 |

**阅读建议**：第 1-4 行是「按测试对象切分」的层级（单元 → 契约 → 集成 →
系统），第 5-8 行是「按可见性/目的切分」的视角（黑盒/白盒/灰盒/功能），
第 9-12 行是「按质量属性切分」的非功能层级（性能/稳定/安全/UI）。同一段
代码会同时属于多个视角——比如对评分器的一批断言，既是单元测试也是白盒
测试；分层不是为了贴标签，而是为了回答「这一次改动，我应该跑哪几层」。

## 2. 测试左移：为什么先跑分

传统 AI 应用的质量保障是「后置」的：模型上线后靠用户反馈、靠人工抽查、
靠事故复盘。三个根本缺陷：

1. **反馈周期太长**：一次劣化从产生到被发现，以天/周计；
2. **无法归因**：提示词改了？模型换版了？上下文变长了？后置反馈说不清；
3. **没有基线**：没有数字就没有「回归」这个概念，全靠体感。

**测试左移（Shift-Left）** 把质量保障推到生成链路的最前端：在模型被集成
进产品之前，先让它跑一组固定的、可判分的任务。每层测试在流水线里的位置
遵循同样的原则——**越便宜、越确定的分层越靠前**：

```
契约测试 ──→ 单元/白盒 ──→ 集成 ──→ 功能（用例集跑分）──→ 系统/端到端
  最便宜          快          中        每次改动都跑          发布前
  （秒级）       （秒级）     （秒级）   （30 秒~分钟级）      （分钟级）
                                                              │
                              性能 / 稳定性 / 安全 / UI ────────┘
                              （按需、gated、人工判断，不阻塞日常）
```

关键前提：**评分必须是确定性的**。只有同样输入永远得到同样分数，分数才能
进基线、做回归对比。这也是 AIQE 的评分器只用关键词命中/长度检查/格式校验
三类可复现判定的原因——LLM-as-judge 在本地低资源环境既不现实（并行驻留
两个模型），也不可复现（同一次输入两次输出不同分）。

## 3. 分层使用决策表

不同的变更场景，触发不同层级——不必每次全量跑 12 层：

| 变更场景 | 该跑哪几层 | 为什么 |
|---|---|---|
| **换模型**（版本/量化/后端） | 全量用例集（功能层：标准+扩展+边界） | 模型行为整体变化，无法预知哪个维度受影响，必须全量过卷 |
| **调 prompt**（提示词改写/优化） | 相关用例（该 prompt 所属类别及其相邻类别） | 影响面限于该任务类型；全量跑也可以，但先跑相关用例拿到快反馈 |
| **改评分器**（judge 规则） | 全量测试 + 全部历史用例重跑 | 评分器是「度量」本身，改它必须先证明新旧分数可比——否则基线全部失真 |
| **改执行器/后端协议**（runner 或 Backend Protocol） | 契约测试 + 集成测试 | 协议破坏是结构性错误，最先在契约层暴露 |
| **加新用例**（扩充用例集） | 新用例 + 相邻类别用例 | 用例集是资产，新增用例必须能独立跑通并产生有意义分数 |
| **改报告/输出格式** | 黑盒（报告结构断言）+ UI（文本断言） | 输出格式是下游消费方的契约 |
| **发布前总检** | 全量用例 + 性能（看 tok/s 报告）+ 安全用例 | 发布前把所有 gated 与慢层补跑一遍 |

## 4. 测试纪律：测产品代码，不自证空转

测试层级的骨架搭得再好，也防不住一类常见事故：**测试全绿，但测试根本没
在测产品**。写每一个测试前，逐条过这五问（本框架的测试纪律清单）：

1. **这个测试 import 了被测的真实模块/函数吗？** 如果在测试体内重新实现
   了一遍被测逻辑——这是自证测试，不是回归测试，停下来改。
2. **断言的是产品行为，还是字符串/数字的自身性质？** 变量是测试函数自己
   现造的、没经过任何产品代码处理——断言测的是语言本身，不是产品。
3. **把产品代码故意改错，这个测试会失败吗？** 写完后做一次思想实验：
   给被测函数塞一个明显 bug（返回值取反、删一个分支），测试仍绿 = 没有
   保护力，重写。
4. **硬编码常量是从哪抄来的？** 测试里的魔数/标签字符串应与产品代码引用
   同一来源，而不是各自手打一遍——两份独立维护的「应该一致」迟早漂移。
5. **需要真实硬件/网络吗？** 需要就用依赖注入/monkeypatch 让核心逻辑可
   离线测，而不是整组跳过、又没人发现它从来没真正跑过。

**修复 bug 后加回归测试，多一步红→绿验证**：先在「bug 还在」的版本上跑，
确认测试真的失败（红），再应用修复确认变绿。只做后一步等于没做——测试
可能从写出来那一刻起就是空转的。把「红→绿」过程写进 commit message，
方便审查者核实，而不是只看到「全部通过」就采信。

## 5. 轻量化边界：哪些设施明确不自己建

「分层齐全」不等于「设施齐全」。通用原则：**优先用既有工具补，确需新增
才新增，新增必须轻量**。以下是本框架明确不建自研设施的项目：

| 不建什么 | 交给谁 | 理由 |
|---|---|---|
| LLM-as-judge 评分器 | 确定性评分（关键词/长度/格式） | 本地低资源环境容不下 judge 模型与测试模型并行；且 LLM 评分不可复现，进不了基线 |
| 覆盖率度量设施 | coverage（手动用，不计门禁） | 门禁化 coverage 会催生「为覆盖率而写」的假测试 |
| 静态代码扫描器 | ruff / mypy（既有工具，只维护门禁命令） | 扫描器是成熟工具，自研纯属重复造轮子 |
| 安全扫描器 | bandit 等可选 dev 依赖（手工使用）+ 用例集注入类用例 + 人工 review | 安全覆盖靠用例与 review，不靠自研扫描器 |
| UI 自动化设施 | pytest capsys 文本断言（CLI）；TestClient 轻量断言（Web，如适用） | 不上 playwright/selenium/快照库——文本断言已足够且零依赖 |
| 压测/soak 平台 | gated 脚本（真机时复用 psutil 等既有设施） | soak 与内存稳定性是发布前专项，非常驻测试 |
| 性能自动门禁 | 报告 + 人工判断 | 本地推理 tok/s 波动大，硬门禁只会产生噪音或被迫放宽到无意义 |
| 新测试框架 | pytest 唯一 | 新框架增加维护面；测试纪律（§4）比框架更关键 |

一句话：**层级覆盖靠设计，设施建设靠克制**——12 层里的大部分，用
pytest + 既有工具 + 一组可运行的示例脚本就能落地，这也是 AIQE 本仓库
的全部测试设施清单。
